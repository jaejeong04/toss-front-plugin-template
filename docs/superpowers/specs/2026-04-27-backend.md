## 1. Context in 30 seconds

- Legacy CRM `SmartDoctorCrm` currently drives a synchronous, modal, local VAN/PG card flow (NICE / KOCES over named pipe to `Dll32Server.exe`).
- We are replacing that path — for 간편수납 (simple receipt) only in v1 — with an **asynchronous, backend-mediated flow** through a **Toss Place Front Plugin** (HTML/JS running in the Toss Android device's in-app browser).
- Two WebSockets meet at **your backend**:
  - **WS A** — CRM workstation ↔ backend
  - **WS B** — Plugin browser ↔ backend
- **The plugin never talks to CRM directly, and CRM never talks to the Toss device directly.** You are the broker.
- Toss docs support card/Samsung Pay/Apple Pay and barcode (Alipay/WeChat) through documented payment responses. Cash/현금영수증 is **verification-gated**: do not build backend behavior that assumes integrated `requestPayment` can include cash, prompt for receipt identity, or cancel no-receipt cash until Toss support or real-device testing confirms it.

## 2. Ownership boundary

### Backend owns (you)

- The `payment_session` and `refund_record` data stores
- WS A and WS B servers (listening sockets, auth, routing)
- Device routing index `(deviceSerialNumber → active plugin WS connection)`
- Session state machine + watchdog/expiry timers
- All backend-side idempotency and duplicate-protection logic
- Forwarding cancel/refund requests to the plugin with all Toss-required fields
- Persistence of the full Toss response so cancels can be reconstructed later

### Frontend/plugin owns (separate team)

- The Toss plugin HTML/JS that calls the Toss SDK
- Translating `session.dispatch` into `sdk.template.render*` calls and eventually `sdk.payment.requestPayment`/`requestPaymentCancel`
- Local storage of `smartdoctor.pendingPayment` (payment key + charged amount context) for crash recovery
- Sending `session.result`/`refund.result` back over WS B

### CRM owns (separate team)

- New `TossPaymentSessionService` that opens WS A and wraps `StartSessionAsync` for the receipt ViewModel
- Writing receipt/cardvan_pay/detail_content rows **after** backend confirms `SUCCEEDED`
- Cancel/refund UI triggers
- Bookkeeping-only retry queue when backend confirms success but CRM write fails

### Toss owns (not us)

- The physical payment authorization (card/barcode, and cash only after the cash blockers are resolved)
- The 14-day device-local cache of SUCCESS results (`[docs: payment.html]` — "TTL 14일, 최대 1,000건")
- The on-device UI during `requestPayment`

## 3. Toss SDK reference you need

These are the only Toss-SDK shapes the backend interacts with. SDK field shapes are sourced from https://docs.tossplace.com/reference/plugin-sdk/front/payment.html and https://docs.tossplace.com/reference/plugin-sdk/front/template.html (fetched 2026-04-24 and re-checked 2026-04-27). Implementation notes call out where the docs are silent.

### 3.1 `sdk.payment.requestPayment(params)` — what the plugin will call with data you send

**Input (the plugin passes these, sourced from your `session.dispatch`):**

```ts
{
  paymentKey: string,         // REQUIRED. "중복되지 않는 고유한 결제 식별자" — we use sessionId here.
  tax: number,                // REQUIRED. Math.floor(price/11) if taxable, else 0
  supplyValue: number,        // REQUIRED. price - tax
  tip: number,                // REQUIRED. Typically 0 in medical CRM
  installment?: number,       // default 0
  timeoutMs?: number,         // default 60000
  localeCode?: 'ko' | 'en',   // default 'ko'
  excludePaymentTypes?: ['CASH']  // Default is not documented. The only documented value is ['CASH'], which excludes cash. [] is not documented.
}
```

**Output (the plugin forwards this to you in `session.result.tossResponse`):**

```ts
{ type: 'SUCCESS' | 'CANCELED' | 'TIMEOUT', response: {...} }
```

On `SUCCESS`, `response.paymentMethod` is one of `'CARD' | 'CASH' | 'BARCODE'` and the rest of `response` varies:

All SUCCESS responses follow `{ type: 'SUCCESS', response: { paymentMethod, <method>: {...}, extraData?: {...} } }`. Fields are nested under `response.card`, `response.barcode`, or `response.cash`, NOT at the top of `response`.

**CARD / Samsung Pay / Apple Pay:**

```ts
{ type: 'SUCCESS', response: { paymentMethod: 'CARD', card: { van: string, timestamp: number, approvalNumber: string, acquirerName: string, acquirerCode: string, issuerName: string, issuerCode: string, cardType: string, balance: number, installment: number, maskedCardNumber: string } } }
```

**BARCODE** (Alipay/WeChat/등):

```ts
{ type: 'SUCCESS', response: { paymentMethod: 'BARCODE', barcode: { van: string, timestamp: number, approvalNumber: string, acquirerName: string, acquirerCode: string, issuerName: string, issuerCode: string, cardType: string, balance: number, installment: number, shopCode: string }, extraData: { vanTransactionManagementId: string } } }
```

**CASH:**

```ts
// With receipt:
{ type: 'SUCCESS', response: { paymentMethod: 'CASH', cash: { isCashReceipt: true, cashReceipt: { van: string, timestamp: number, issuerType: 'CONSUMER' | 'BUSINESS', issuanceType: 'PHONE' | 'BUSINESS_NUMBER' | 'CARD', identityNumber: string, maskedIdentityNumber: string, approvalNumber: string, isSelfIssuance: boolean } } } }

// Without receipt:
{ type: 'SUCCESS', response: { paymentMethod: 'CASH', cash: { isCashReceipt: false } } }
```

The returned `cashReceipt` object is at `response.cash.cashReceipt`, not at the top of `response`.

**Cash blockers:** the Toss docs do not state how integrated `requestPayment` includes cash, whether it prompts for phone/business number, or how to cancel a CASH response with `isCashReceipt: false`. The no-receipt response has no `timestamp` or `approvalNumber`, while `requestPaymentCancel` requires both. Backend v1 must exclude cash from the integrated flow until these are resolved.

### 3.2 `sdk.payment.requestPaymentCancel(params)` — what the plugin will call when backend dispatches a refund

**Input you must supply to the plugin via `session.dispatch` (type cancel):**

```ts
{
  paymentKey: string,                 // REQUIRED — the ORIGINAL sessionId
  paymentMethod: 'CARD' | 'CASH' | 'BARCODE',   // REQUIRED — from original SUCCEEDED response. CASH is usable only when original cash.cashReceipt exists.
  tax: number,                        // REQUIRED — original
  supplyValue: number,                // REQUIRED — original
  tip: number,                        // REQUIRED — original
  timestamp: number,                  // REQUIRED — from original: response.card.timestamp | response.barcode.timestamp | response.cash.cashReceipt.timestamp
  approvalNumber: string,             // REQUIRED — from original: response.card.approvalNumber | response.barcode.approvalNumber | response.cash.cashReceipt.approvalNumber
  installment?: number,               // default 0
  timeoutMs?: number,                 // default 60000
  localeCode?: 'ko' | 'en',           // default 'ko'
  extraData?: { vanTransactionManagementId: string },   // REQUIRED for BARCODE; omit otherwise
  isSelfIssuance?: boolean            // for CASH with receipt, pass through
}
```

Partial cancel is **not documented** on the Toss reference page. For v1, send full-amount values identical to the original payment. If finance requires partial cancel we will raise a change request. CASH with `isCashReceipt: false` is not cancellable under this documented field contract; reject with `REFUND_NOT_SUPPORTED_CASH_NO_RECEIPT` unless Toss supplies a documented alternative.

### 3.3 `sdk.payment.getPayment({ paymentKey })` — used by plugin for crash recovery

Returns the same SUCCESS response shape as above. Throws `PAYMENT_NOT_FOUND` if no cached result exists (cache is SUCCESS-only, 14 days, 1000 records max — these are the Toss device's cache limits, not yours).

**Device-scope verbatim from Toss docs:** "결제를 요청한 단말기에서만 조회할 수 있습니다. 다른 단말기나 서버에서는 조회할 수 없습니다." (Same wording applies to `getPaymentCancel`.)

**Consequence:** a payment approved on device A cannot be recovered from device B, even when both are bound to the same merchant. Backend's `getPayment` is unreachable directly — only the plugin on the physical device can retrieve. **Backend must persist the full `tossResponse` at approval time, because it cannot fetch it later via any `sdk.*` method.**

### 3.4 `renderOrderPage` input — you construct this and send in `session.dispatch`

```ts
order: {
  items: [
    {
      label: string,           // e.g. "진료비 (홍길동)"
      value: number,           // line amount in KRW
      quantity?: number,       // default 1
      options?: [
        { type: 'option' | 'discount', label: string, value: number }
      ],
      imageUrl?: string
    }
  ],
  discounts: [                  // max 3
    { label: string, value: number }
  ],
  summary: {
    totalAmount: number,        // sum shown to user
    discountAmount?: number,
    remainingPoint?: number,
    paidAmount?: number,
    changeAmount?: number,
    earned?: { label: string, value: number, suffix: string } | { label: string, value: string }
  }
}
```

`earned` is a discriminated union: when `value` is `number`, `suffix: string` is REQUIRED; when `value` is `string`, no suffix.

### 3.5 `renderUsePointPage` input — plugin constructs this from `pointContext`

The plugin builds this shape itself from the `pointContext` you send in `session.dispatch`. Backend does not serialize this exact shape.

```ts
points: [ { name: string, amount: number } ],   // plugin sets name = "사용 가능한 메디캐시", amount = computed usable cash
summary: {
  pointUsedAmount: number,   // plugin: computed usable cash (default shown as "전액 사용" preview)
  paymentAmount: number      // plugin: treatmentTotal - pointUsedAmount
},
cta: { cancel: {...}, submit: {...} }   // [사용 안 함] / [전액 사용] binary
```

**Per the 메디캐시 PDF (p.9):**

- Plugin computes `usableCash = floor(min(availableBalance, treatmentTotal) / 100) * 100`
- If `usableCash < pointContext.minUseAmount`, plugin SKIPS this template entirely and goes straight to `renderOrderPage`
- Binary choice: `[전액 사용]` applies `usableCash`, `[사용 안 함]` applies 0

**Backend responsibility:** provide the `pointContext` shape in `session.dispatch.pointContext`:

```ts
pointContext: {
  availableBalance: number,      // customer's 메디캐시 balance (unit: 캐시)
  minUseAmount: number,          // hospital's min-use threshold (from 캐시닥 for hospital config)
  earnAmount: number,            // amount earned by this payment (for display on renderOrderPage)
  earnLabel: string,             // label for earned display (e.g., "이번 결제 적립")
  earnSuffix: string             // unit suffix (e.g., "캐시")
}
```

## 5. Plugin identity & trust

The plugin does not log in and does not hold a backend-issued token. It identifies itself solely by the **device serial number** returned from `sdk.app.getSerialNumber()` ([`front-plugin-js/home.html:41`](../../front-plugin-js/home.html)). That serial is sent on the WS B URL (`?serial=<serialNumber>`) and again in the `device.register` payload (§7.2).

**Open question — owned by backend team:** how does the backend decide a connecting serial is legitimate? Options range from "fully open: any serial that connects is accepted, on the assumption that Toss has gated the partner-portal device list" to "thin registry: an out-of-band-populated `plugin_device(serial, merchant_id, registered_at)` table; reject unknown serials with WS close `4403`". This spec deliberately does not pick one — pick the model that matches your security posture and add the corresponding validation rule to §7.2 / §9 once decided. Track in §15.

## 6. WebSocket A — CRM ↔ Backend

### 6.1 Connection

**URL:** `wss://<backend>/crm?token=<workstation_token>`

- `<workstation_token>` is CRM-side — mechanism TBD by CRM auth integration. For v1 assume it comes from an existing CRM auth endpoint not in scope here. Treat as a signed bearer.
- On invalid/expired token: close with code `4401`.
- Heartbeat: Application-level heartbeat (NOT WS protocol ping, which browsers cannot send from JS): client sends `{"type":"ping"}` every 20s. Server responds `{"type":"pong"}`. Three missed pings → backend drops connection.

### 6.2 Message envelope

All messages use this envelope:

```json
{ "type": "<message.type>", "payload": { ... } }
```

### 6.3 Inbound (CRM → Backend)

#### `session.create`

CRM starts a new 수납.

```json
{
  "type": "session.create",
  "payload": {
    "clientRequestId": "c1r_01HXX...",
    "deviceSerialNumber": "TF-000123456",
    "workstationId": "ws_0001",
    "crmOrigin": {
      "organizationId": "ORG00001",
      "customerNumber": "CUST000123",
      "insuranceSeqNo": 1,
      "medicalClinicSeqNo": 42,
      "reservationSeqNo": null,
      "customerName": "홍길동"
    },
    "amount": {
      "supplyValue": 27273,
      "tax": 2727,
      "tip": 0
    },
    "orderSnapshot": {
      "items": [
        {
          "label": "진료비 (홍길동)",
          "value": 30000,
          "quantity": 1
        }
      ],
      "discounts": [],
      "summary": {
        "totalAmount": 30000,
        "earned": { "label": "이번 결제 적립", "value": 200, "suffix": "캐시" }
      }
    },
    "pointContext": {
      "availableBalance": 5000,
      "minUseAmount": 1000,
      "earnAmount": 200,
      "earnLabel": "이번 결제 적립",
      "earnSuffix": "캐시"
    }
  }
}
```

**Validation:**

- `amount.supplyValue + amount.tax + amount.tip` must be a positive integer
- `amount.tip` MUST be `0` in v1. The plugin's 진료 금액 display (PDF p.10) and its usable-cash formula (PDF p.9) both use `supplyValue + tax` as the treatment total; a non-zero tip would diverge these. Reject with `INVALID_REQUEST` if tip ≠ 0.
- `deviceSerialNumber` must satisfy whatever trust check §5 resolves to (e.g., known in `plugin_device` registry, if one exists). Until §5 is decided, treat any serial as acceptable for v1 development.
- `clientRequestId` must be unique per workstation within 5 minutes (idempotency — see §11)

**Response:** `session.ack` (§6.4) immediately, then `session.status` and finally `session.result` as state progresses.

#### `session.abort`

CRM user clicked cancel. CRM UI should only surface this action while backend status is `CREATED` or `DISPATCHED`; the button must be disabled when status is `IN_PROGRESS` (see §6.3 IN_PROGRESS branch below — server rejects, this is a defense-in-depth guard).

```json
{
  "type": "session.abort",
  "payload": { "sessionId": "ses_01HXX..." }
}
```

**Behavior:**
Backend emits `session.abort.ack` immediately; then later emits `session.result` when the terminal state is known.

- If current status is `CREATED` or `DISPATCHED`: transition to `CANCELED`, send `session.result` to CRM, and (if `DISPATCHED`) forward a cancel signal to plugin (it may have rendered the order page but not called `requestPayment` yet — plugin should return to idle).
- If current status is `IN_PROGRESS`: reject the abort. Respond with `session.abort.ack` `{ status: 'REJECTED', reason: 'IN_PROGRESS_NOT_ABORTABLE' }`. Client should have prevented this call via UI but defensive server-side rejection guards against race conditions.
- If current status is a terminal state: return `session.result` with existing state and log the late abort as a no-op.

#### `refund.create`

CRM user clicked 수납취소 on a previously-succeeded session.

```json
{
  "type": "refund.create",
  "payload": {
    "originalSessionId": "ses_01HXX...",
    "clientRequestId": "c1r_01HXY..."
  }
}
```

**Validation:**

- `originalSessionId` must exist and have status `SUCCEEDED`
- There must not already be a non-terminal refund for this session
- **Refund time window is not specified by Toss docs.** The 14-day device cache in §3.3 only bounds the plugin's ability to RECOVER an unknown result via `getPayment` — it does not bound refund eligibility, because backend already stores the full Toss response and re-supplies `timestamp`/`approvalNumber` into `requestPaymentCancel` regardless. Backend should not pre-reject based on age; Toss's own response will surface a denial if the card network rejects the cancel.

## 7. WebSocket B — Plugin ↔ Backend

### 7.1 Connection

**URL:** `wss://<backend>/plugin?serial=<deviceSerialNumber>`

- `<deviceSerialNumber>` is read by the plugin from `sdk.app.getSerialNumber()` and URL-encoded ([`front-plugin-js/home.html:45-49`](../../front-plugin-js/home.html)). There is no plugin-side token. See §5 for the trust model open question.
- Heartbeat: Application-level heartbeat (NOT WS protocol ping, which browsers cannot send from JS): client sends `{"type":"ping"}` every 20s. Server responds `{"type":"pong"}`. Three missed pings → backend drops connection.
- On a serial that fails whatever trust check §5 resolves to: close with code `4403`.

### 7.2 Inbound (Plugin → Backend)

#### `device.register`

First message after connect.

```json
{
  "type": "device.register",
  "payload": {
    "serialNumber": "TF-000123456",
    "sdkVersion": "v0"
  }
}
```

**Validation:** `payload.serialNumber` must match the `?serial=` query parameter from §7.1. Mismatch → close with code `4403`. Any further trust check (e.g., serial-is-registered) follows §5.

**Side effect:** backend stores `(device_serial_number → this connection)` in its routing index. If a previous connection existed for the same serial, **close the old one** and adopt the new one. For any sessions currently in DISPATCHED, IN_PROGRESS, or EXPIRED bound to this serial, immediately send `session.reconcile` on the new connection so the plugin can call `getPayment` if it has not already self-recovered (scope matches §12 step 1).

#### `session.claim`

Plugin acknowledges it's about to show the order page.

```json
{
  "type": "session.claim",
  "payload": { "sessionId": "ses_01HXX..." }
}
```

**Backend action:** transition status `DISPATCHED` → `IN_PROGRESS`. If current status is `DISPATCHED`: transition to `IN_PROGRESS` and ack implicitly (no response). If current status is `IN_PROGRESS` and the claim is from the same serial: treat as idempotent no-op (plugin likely reloaded after a crash; return current state via `session.status` so the plugin can proceed to `getPayment` recovery if needed). Other states: return `error`.

#### `session.chargeContext`

Plugin reports the exact post-point amount context immediately before calling `sdk.payment.requestPayment`. Backend persists this before the Toss UI begins so late recovery still has the fields required by future cancel/refund dispatch.

```json
{
  "type": "session.chargeContext",
  "payload": {
    "sessionId": "ses_01HXX...",
    "pointUseAmount": 1000,
    "chargedSupplyValue": 26364,
    "chargedTax": 2636
  }
}
```

**Validation:** session must be `IN_PROGRESS` for the same device serial; `chargedSupplyValue + chargedTax + original.tip + pointUseAmount` must equal the original treatment total (`payment_session.supply_value + payment_session.tax + payment_session.tip`). Persist `point_use_amount`, `toss_charged_supply_value`, and `toss_charged_tax`. If `session.result` later repeats the same fields, validate they match.

#### `session.result`

Plugin reports the Toss SDK outcome for a payment session.

```json
{
  "type": "session.result",
  "payload": {
    "sessionId": "ses_01HXX...",
    "pointUseAmount": 0,
    "chargedSupplyValue": 27273,
    "chargedTax": 2727,
    "tossResponse": {
      "type": "SUCCESS",
      "response": {
        /* one of the three shapes in §3.1 */
      }
    }
  }
}
```

**Backend responsibilities:**

- Validate `tossResponse.response.paymentMethod` is one of `CARD | CASH | BARCODE`
- Reject CASH with `response.cash.isCashReceipt === false` as `REFUND_NOT_SUPPORTED_CASH_NO_RECEIPT` unless the cash blockers are resolved; this response lacks the fields required for future Toss cancel.
- Persist the full `tossResponse` to `payment_session.toss_response_json`
- Extract and persist `toss_payment_method = tossResponse.response.paymentMethod`, `toss_approval_number` from `tossResponse.response[paymentMethod].approvalNumber` (where `[paymentMethod]` is `card` / `barcode` / `cash.cashReceipt`), `toss_timestamp` similarly, and (if BARCODE) `toss_van_tx_mgmt_id = tossResponse.response.extraData.vanTransactionManagementId`
- Persist or validate `point_use_amount = payload.pointUseAmount`, `toss_charged_supply_value = payload.chargedSupplyValue`, `toss_charged_tax = payload.chargedTax` — these are the post-point amounts actually passed to Toss and are REQUIRED for future refund dispatch per §3.2. If a late recovery result omits them and no prior `session.chargeContext` exists, do not auto-finalize as `SUCCEEDED`; flag for manual reconciliation.
- Transition state to `SUCCEEDED | CANCELED | TIMEOUT | FAILED` based on `tossResponse.type`
- Forward to CRM via `session.result` on WS A

{

    "refundId": "rfd_01HXY...",
    "tossResponse": {
      "type": "SUCCESS",

        /* Toss cancel response */
      }

Triggered when backend suspects an EXPIRED session may actually have succeeded on the device (see §12).

## 8. Session state machine

```
            session.create (WS A)
                  │
                  ▼
             [CREATED]
                  │
                  │ device WS B connected for this serial?
           ┌──────┴──────┐
          yes            no
           │              │
           ▼              ▼
      emit session.    set status=FAILED,
      dispatch,        reason=DEVICE_OFFLINE,
      set status=      after 10s grace period
      DISPATCHED       for device to register;
                       emit session.result
                       to CRM, DONE
           │
           │ (plugin doesn't claim in 30s → FAILED / PLUGIN_UNRESPONSIVE)
           ▼
      (plugin claims)
           │
           ▼
     [IN_PROGRESS]
           │
       ┌───┴─────────────────┐
      plugin result        watchdog fires
       │                      │
       ▼                      ▼
  based on type:          [EXPIRED]
  SUCCESS → SUCCEEDED     emit session.result
  CANCELED → CANCELED     (FAILED, EXPIRED)
  TIMEOUT → TIMEOUT       DONE
       │
       ▼
 emit session.result
 DONE
```

**Legal terminal states:** `SUCCEEDED`, `FAILED`, `CANCELED`, `TIMEOUT`, `EXPIRED`.

**Watchdog rules:**

- `CREATED` for > 10s with no WS B match → `FAILED` (DEVICE_OFFLINE)
- `DISPATCHED` for > 30s with no `session.claim` → `FAILED` (PLUGIN_UNRESPONSIVE)
- `IN_PROGRESS` for > `timeoutMs + 30s` with no `session.result` → `EXPIRED`. Reconciliation runs on the plugin's next `device.register` per §12 (which covers DISPATCHED, IN_PROGRESS, and EXPIRED sessions).

**Abort semantics:** aborts on `IN_PROGRESS` sessions are **rejected** (see §6.3). CRM UI must disable the abort button while status is `IN_PROGRESS` to prevent the user from reaching this state. If a race produces an abort on `IN_PROGRESS`, backend responds with `session.abort.ack { status: REJECTED, reason: IN_PROGRESS_NOT_ABORTABLE }` and takes no other action; the session continues to its natural terminal state.

## 9. Device routing

- Every active WS B connection is keyed by the `serialNumber` it presented on connect (§7.1) and re-asserted via `device.register` (§7.2).
- Backend maintains an in-memory index `Map<serial_number, WsConnection>`
- On `session.create.deviceSerialNumber`:
  - Look up the connection
  - If exists: send `session.dispatch`, set status `DISPATCHED`
  - If not: immediately terminate session as `FAILED / DEVICE_OFFLINE`
- One device = one active connection. New connection with same serial replaces old.

**Multi-workstation note:** CRM workstations each have their own config-stored `TossDeviceSerialNumber` (CRM-side config key — see CRM spec §8). Backend does not know about workstations beyond using them for WS A auth — the workstation → device mapping lives entirely on the CRM side.

**Hardware swap safety:** if a `device.register` arrives for a serial that currently has non-terminal sessions bound to a previous WS connection, backend may still replace the connection (§7.2), but any session in DISPATCHED/IN_PROGRESS on the old connection cannot be reconciled from a physically different unit. CRM operators must be alerted when replacing a device mid-session. The `TossDeviceSerialNumber` config change on CRM side should be blocked while any non-terminal session is bound to the old serial.

## 10. Timeouts

| Timer                                     | Value                                              | Who sets         | What happens on fire                                                                                          |
| ----------------------------------------- | -------------------------------------------------- | ---------------- | ------------------------------------------------------------------------------------------------------------- |
| WS heartbeat miss                         | 3 × 20s                                            | Backend          | Drop connection                                                                                               |
| `CREATED` waiting for device              | 10s                                                | Backend watchdog | → `FAILED` (DEVICE_OFFLINE)                                                                                   |
| `DISPATCHED` waiting for claim            | 30s                                                | Backend watchdog | → `FAILED` (PLUGIN_UNRESPONSIVE)                                                                              |
| `IN_PROGRESS` waiting for result          | `timeoutMs + 30s`                                  | Backend watchdog | → `EXPIRED`, reconcile later                                                                                  |
| Toss SDK `requestPayment` timeout         | 60000 (default)                                    | Plugin           | Plugin sends `session.result` with `type: 'TIMEOUT'`                                                          |
| Plugin-side recovery cache (`getPayment`) | 14 days, max 1000 records, SUCCESS only            | Toss             | Beyond this, `getPayment` throws `PAYMENT_NOT_FOUND`; matters only for reconciliation (§12), NOT for refunds. |
| `getPaymentCancel` cache                  | same as `getPayment` (14 days, 1000, SUCCESS only) | Toss             | Plugin's cancel-result lookup is also device-local.                                                           |

Source for Toss cache: `[docs: https://docs.tossplace.com/reference/plugin-sdk/front/payment.html]` — "TTL 14일, 최대 1,000건이 저장됩니다. SUCCESS 결과만 캐시되며…"

**Refund eligibility window is not specified by Toss docs `[GAP]`.** Backend should attempt the cancel regardless of age and surface whatever Toss returns.

## 11. Idempotency

- `session.create.clientRequestId` must be dedup'd: if the same `(workstation_token, clientRequestId)` pair arrives twice within 5 minutes, return the existing `sessionId` in `session.ack` instead of creating a new one.
- `refund.create.clientRequestId` — same rule per session.
- `sessionId` is **used as-is as `paymentKey`** on Toss. Toss's own duplicate-protection (if any for `requestPayment`) is device-local and not something backend can rely on, so backend must never reuse a `sessionId` across different CRM intents.
- `session.result` on WS B may arrive multiple times if the plugin reconnects mid-flight. Second and later arrivals with the same `sessionId` and identical approval number (extracted from `tossResponse.response.card.approvalNumber` / `response.barcode.approvalNumber` / `response.cash.cashReceipt.approvalNumber` depending on `paymentMethod`) are no-ops. CASH without `cashReceipt` has no documented approval number and is unsupported for v1. Arrivals with a DIFFERENT approvalNumber for the same `sessionId` are a hard error — log loudly and alert.

## 12. Reconciliation (recovery)

When a session has been `EXPIRED` by watchdog but the device may have actually approved:

1. On `device.register`, look for sessions bound to this serial in **any non-terminal state beyond CREATED** (DISPATCHED, IN_PROGRESS, or EXPIRED). For each, send `session.reconcile`. Reconciliation is only meaningful when the registering device is the SAME physical unit that received the original dispatch. If the serial has been re-bound to different hardware (device swap or factory reset), `sdk.payment.getPayment` will return PAYMENT_NOT_FOUND because the cache is device-local (§3.3 verbatim quote). In that case the session remains EXPIRED and must be handled by CRM-side bookkeeping correction. Toss does not expose a hardware-fingerprint API, so serial-match is the only practical check we have.
2. For each, send `session.reconcile` to the plugin:
   ```json
   {
     "type": "session.reconcile",
     "payload": { "sessionId": "ses_...", "paymentKey": "ses_..." }
   }
   ```
3. Plugin calls `sdk.payment.getPayment({ paymentKey })`. If it returns a response, plugin replies:
   ```json
   {
     "type": "session.result",
     "payload": {
       "sessionId": "ses_...",
       "pointUseAmount": 1000,
       "chargedSupplyValue": 26364,
       "chargedTax": 2636,
       "late": true,
       "tossResponse": { "type": "SUCCESS", "response": { ... } }
     }
   }
   ```
4. If plugin replies with `PAYMENT_NOT_FOUND`, backend keeps `EXPIRED` status.
5. If the plugin cannot supply amount fields but backend already persisted `session.chargeContext`, backend may use the persisted values. If neither source has amount fields, keep the session `EXPIRED` and alert for manual reconciliation; do not mark it `SUCCEEDED` because future refunds would lack the original charged tax/supply split.
6. If reconciliation uncovers a SUCCESS after an `EXPIRED`, forward a late `session.result` to CRM with a new field `"late": true`. CRM will handle via its bookkeeping-only retry queue.

(Plugin-side detail: on every page load the plugin also self-checks `sdk.storage.get({key:"smartdoctor.pendingPayment"})` and posts result proactively — so backend doesn't always need to initiate reconciliation. If storage was wiped, backend depends on the already-persisted `session.chargeContext`; if that is missing, manual reconciliation is required.)

## 13. Error codes

Backend-emitted `failureReason` values:

| Code                                   | When                                                                                                                             |
| -------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `DEVICE_OFFLINE`                       | No active WS B for the serial at dispatch time                                                                                   |
| `PLUGIN_UNRESPONSIVE`                  | Dispatched but no `session.claim` in time                                                                                        |
| `INVALID_REQUEST`                      | Schema validation failed on inbound message                                                                                      |
| `REFUND_REJECTED_BY_TOSS`              | Toss returned non-SUCCESS on `requestPaymentCancel` — the `tossResponse` carries the specific reason                             |
| `REFUND_NOT_SUPPORTED_CASH_NO_RECEIPT` | Original CASH response had `isCashReceipt: false`, so the documented response lacks cancel-required `timestamp`/`approvalNumber` |
| `ALREADY_REFUNDED`                     | Refund attempt when an active refund exists                                                                                      |
| `INVALID_STATE_TRANSITION`             | e.g. `session.claim` on a terminal session                                                                                       |
| `TOSS_AUTH_FAILED`                     | Only if Toss's own error surfaces in `tossResponse.type` (rare)                                                                  |
| `INTERNAL`                             | Anything else — alert, paging                                                                                                    |

## 14. Acceptance criteria (backend must pass)

Write tests that prove each:

1. **Happy path card.** `session.create` → device matches → `session.dispatch` sent → plugin `session.claim` → plugin `session.result` with CARD success → CRM receives `session.result` SUCCEEDED with full tossResponse → row in `payment_session` has all toss\_\* fields populated.
2. **Happy path barcode.** Same as (1) but `paymentMethod: 'BARCODE'` → `toss_van_tx_mgmt_id` populated.
3. **Cash is gated.** Integrated payment dispatch excludes cash with `excludePaymentTypes: ["CASH"]`. If a CASH result is received before the cash blockers are resolved, backend preserves it for audit but treats `cash.isCashReceipt: false` as unsupported for Toss refund (`REFUND_NOT_SUPPORTED_CASH_NO_RECEIPT`) and does not claim full-cancel support for it.
4. **Device offline.** `session.create` with a serial that has no active WS B → `session.result FAILED/DEVICE_OFFLINE` within 10s.
5. **Plugin unresponsive.** Dispatched but plugin never claims → `session.result FAILED/PLUGIN_UNRESPONSIVE` within 30s of dispatch.
6. **Idempotent create.** Same `clientRequestId` twice within 5 minutes → second returns the same `sessionId`, no duplicate session row.
7. **Duplicate result.** Plugin sends `session.result` for the same `sessionId` twice, same `approvalNumber` → second is a no-op; single CRM notification.
8. **Late result after expiry.** Watchdog expires a session; plugin later sends `session.result` with SUCCESS plus charged amount fields, or backend has prior `session.chargeContext` → backend records late success, forwards to CRM with `"late": true`.
9. **Full cancel happy path.** Refund on a SUCCEEDED CARD session → plugin receives all required cancel fields → refund SUCCEEDED → CRM receives `refund.result`.
10. **Cancel after Toss rejection.** Refund dispatched, Toss returns `type !== 'SUCCESS'` → `refund_record.status = FAILED`, `failureReason = REFUND_REJECTED_BY_TOSS`, CRM receives `refund.result` with the full `tossResponse` for diagnosis.
11. **Concurrent refund race.** Two `refund.create` for the same session in parallel → only one creates a refund_record, the other returns `ALREADY_REFUNDED`.
12. **Abort on IN_PROGRESS is rejected.** `session.abort` on `IN_PROGRESS` session → backend returns `session.abort.ack { status: REJECTED, reason: IN_PROGRESS_NOT_ABORTABLE }`; no side effects on the session; session continues to its natural terminal state. (CRM UI should prevent this call, but the server-side guard must exist.)
13. **Abort on DISPATCHED succeeds.** `session.abort` on `DISPATCHED` session (plugin hasn't called `requestPayment` yet) → backend emits `session.abort` to plugin (§7.3), transitions session to CANCELED, emits `session.abort.ack { status: CANCELED }` to CRM, and emits `session.result { status: CANCELED }`. Plugin returns to idle without calling `requestPayment`.
14. **Plugin reconnect mid-flight (EXPIRED).** During `IN_PROGRESS`, kill plugin's WS and wait for the watchdog to transition the session to EXPIRED. Then re-register → backend's `session.reconcile` triggers plugin to call `getPayment` → result flows normally with `"late": true` flag.
15. **Plugin reconnect mid-flight (non-terminal).** During `IN_PROGRESS` (pre-expiry), plugin's WS drops and re-registers. Backend sends `session.reconcile` immediately for the dangling session; plugin calls `getPayment`; if found, returns SUCCESS result; if not found, nothing changes and watchdog will still expire it on schedule.
16. **Serial mismatch on register.** `device.register.payload.serialNumber` does not match the `?serial=` query parameter from the WS B URL → backend closes WS with 4403. (Any registry-based "unknown serial" rejection is gated on §5 and is OUT of scope for this acceptance criterion until that OQ is resolved.)
17. **Connection replacement.** Second plugin connects with the same serial → old connection is closed and new one takes over; any DISPATCHED/IN_PROGRESS/EXPIRED session receives `session.reconcile` within a bounded time; plugin responds with the cached result or PAYMENT_NOT_FOUND.

## 15. Open questions backend must decide / confirm

These need backend input before implementation wraps:

1. **CRM workstation auth mechanism for WS A.** Is there an existing CRM auth service we plug into, or does backend issue workstation tokens too? If backend issues them, design an equivalent of §5 for workstations. 6. **Log retention** and **PII handling** for `toss_response_json` (contains masked card number, masked identity number). Confirm with compliance what TTL is acceptable.

**Cross-team open questions affecting backend:**

6. `[GAP]` **Partial cancel support**: Toss docs ambiguous (no mention on payment.html). — **Owner: backend team, verify with Toss support; if unsupported, v1 stays full-cancel-only**
7. `[GAP]` **Merchant/franchise ID**: Toss `sdk.app.getMerchant()` returns `{id, name, businessNumber}`. Which maps to legacy `CARDVAN_PAY.JUM_NO`? — **Owner: backend + CRM, verify on onboarding** (also tracked in CRM spec)

9. `[GAP]` **Toss failure-code → Korean label mapping**: error code lists exist only for `getPayment`/`getPaymentCancel` (`INVALID_PARAMS`, `PAYMENT_NOT_FOUND`).
